                                             Prefix Executability: Evaluating Tool-Using Agents
                                                           Beyond Final Success

                                                                                             Abstract
                                                   Tool-use benchmarks often score agents by final task success, but terminal out-
                                                   comes can obscure whether the intermediate tool-call trajectory was executable.
                                                   We propose prefix executability as a trajectory-level evaluation protocol for tool-
                                                   using agents. The protocol measures whether every prefix of a predicted tool-call
                                                   sequence remains executable under tool schemas, state preconditions, and data
                                                   dependencies, and summarizes reliability using Prefix Executability Curves (PEC),
                                                   First-Error Depth (FED), Trajectory Executability Rate (TER), horizon-normalized
                                                   AUC-PEC, and Recovery Rate (RR). We instantiate the protocol on stratified
                                                   samples from BFCL-v3 multi-turn and ToolSandbox, and on the complete Air-
                                                   line/Retail base splits of τ 3 -bench. We observe that outcome-only and prefix-level
                                                   rankings diverge: agents whose execution is conditioned on an unverified plan often
                                                   achieve higher point-estimate final success than non-plan-conditioned baselines
                                                   while substantially lowering TER and AUC-PEC. These divergences are precisely
                                                   the failure modes that prefix executability is designed to expose: they reveal
                                                   whether apparent success rests on an executable trajectory, where invalidity first
                                                   enters, and whether success follows recovery from an earlier failure. As a validation
                                                   intervention, explicit pre-execution plan checking can improve executable-prefix
                                                   survival while maintaining competitive terminal success. These results show that
                                                   final success alone is insufficient for evaluating tool-use agents and that prefix-
                                                   level executability provides an actionable reliability signal for comparing agents,
                                                   diagnosing failures, and assessing validation mechanisms.


                                         1     Introduction
                                         Tool-using language agents operate over APIs, user-defined tools, and interactive software envi-
                                         ronments where correctness depends on more than a final answer. A valid run must maintain an
                                         executable sequence of intermediate actions while respecting tool schemas, cross-step dependencies,
                                         and evolving environment state [1–4]. This requirement is especially acute in multi-turn settings,
                                         where an early invalid call can corrupt later state or force the agent into recovery behavior that is
                                         invisible to outcome-only scoring [3–6]. Consider a service workflow in which an agent first retrieves
                                         a record, then passes the returned identifier to update, payment, or notification tools. A later call may
                                         be syntactically well formed but non-executable if it references a stale identifier, skips a required
                                         precondition, or applies an update before the corresponding state exists; a subsequent repair can still
                                         produce the desired final state while hiding where the trajectory first became invalid.
                                         Recent evaluation work has moved beyond simple terminal accuracy. T-Eval decomposes tool use
                                         into step-wise subskills [7]; ToolSandbox evaluates task-specified intermediate and final conditions
                                         and checks for prohibited states or events [4]; TRAJECT-Bench scores tool selection, argument
                                         correctness, and dependency ordering over full trajectories [8]; ToolPRMBench and AgentProcess-
                                         Bench assess local process quality [9, 10]; and procedure-aware evaluation shows that nominally
                                             ∗ Correspondence: Amir.Rezaeian@oracle.com.

successful runs can still violate task procedures [11]. TRACE adds reference-free assessment of
efficiency, hallucination, and adaptivity over tool-use trajectories [12]. Robustness studies further
probe query perturbations, tool-set changes, and injected execution faults [13, 14]. These efforts
make a remaining gap clear: standard metrics still rarely quantify how long a naturally generated
rollout remains executable before its first invalid prefix, or how often final success is achieved only
after entering a failure regime.
Prefix executability complements these evaluations by checking the execution feasibility of the
actual emitted rollout under explicit tool and state semantics. It credits alternative executable action
sequences without requiring one gold path and records first failure, survival, and recovery. Appendix A
compares what prior evaluation protocols measure.
We study prefix-level executability failures: trajectory prefixes that may look plausible as text but
are non-executable under the available tool schema, explicit preconditions, cross-step references, or
current environment state. We argue that prefix executability is a missing reliability axis because final
success and reference-trajectory match conflate three questions: how long the rollout remains valid,
where validity first breaks, and whether later actions recover from the break. We therefore formalize
executable prefixes and report a metric family centered on Prefix Executability Curves (PEC),
First-Error Depth (FED), horizon-normalized AUC-PEC, Trajectory Executability Rate (TER), and
Recovery Rate (RR). These metrics primarily diagnose reliability; when reported alongside trajectory
length, latency, or monetary cost, they also support efficiency-sensitive analysis by distinguishing
short, valid rollouts from long or failure-prone ones.
These distinctions are operationally important in cost-sensitive tool use. In workflows that trigger
external transactions, consume scarce resources, modify persistent state, or require human escalation,
the depth of the first invalid action can determine both the cost of failure and the feasibility of recovery.
Prefix executability therefore provides a practical evaluation signal for deciding not only whether an
agent eventually succeeds, but also whether execution remains uninterrupted or requires recovery
along the way.
The paper is evaluation-first. We deliberately use a minimal Dual-Loop planner-verifier intervention
only as a controlled probe: we test whether pre-execution validation improves those metrics even
when final success rankings tell a different story. This framing separates the evaluation contribution
from the particular intervention and lets us ask when plan conditioning helps tool use, and when it
amplifies invalid intermediate structure.
Our contributions are:
1. We formalize executable prefixes for tool-using agents and define PEC, FED, TER, AUC-PEC, and
   RR as a prefix-level evaluation protocol for variable-horizon trajectories. Appendix B establishes
   exact properties and consistency under explicit sampling assumptions.
2. We instantiate the protocol on BFCL v3 multi-turn and ToolSandbox with stratified 200-example
   samples, and on all 164 Airline/Retail base-split tasks in τ 3 -bench, using shared task IDs across
   methods and models, and task-level confidence intervals.
3. We show that outcome-only and prefix-level rankings can diverge: unverified plan conditioning
   can improve final success while sharply reducing executability, whereas pre-execution validation
   consistently improves TER, AUC-PEC, and early PEC across three LLM conditions on BFCL
   v3 and ToolSandbox. A representative BFCL setting illustrates the pattern: an unverified plan-
   conditioned executor can reach the correct terminal outcome while emitting invalid intermediate
   tool-call prefixes, whereas Dual-Loop preserves terminal performance while restoring prefix
   executability. The τ 3 -bench audit further demonstrates that prefix reliability and terminal success
   can rank methods differently.
We evaluate BFCL v3 and ToolSandbox because together they cover multi-step function composition
and stateful, on-policy tool interaction [3, 4]. The Airline/Retail audit evaluates the protocol in
policy-constrained user–agent–environment interaction in τ 3 -bench. Together, the three benchmarks
cover 564 task instances per model–method condition and 6,768 rollouts.

2     Prefix-Level Executability Evaluation
2.1   Executable Prefixes

We model an agent rollout as a predicted trajectory τ̂ = (a1 , . . . , aT ), where each ordinary action
at is a tool invocation with arguments. Let st denote the environment state immediately before
executing at . An action is executable if the selected tool is available, the arguments conform to its
schema, all explicit preconditions hold in st , and any referenced intermediate values are present and
type-consistent.
A prefix τ̂≤k = (a1 , . . . , ak ) is executable if every action in the prefix executes successfully under
the states induced by prior actions. This definition evaluates feasibility rather than agreement with a
single reference trajectory, which matters because many tool tasks admit multiple valid execution
orders or alternative executable call sequences [3, 4, 6].
The benchmark-side scorer is deterministic and uses no LLM judge. It checks exposed tools, argument
binding and validators, current and type-compatible references, information availability, explicit
preconditions, and benchmark acceptance of the transition. Accepted actions advance state; the first
rejection fixes FED. Prefix replay then stops, while the full rollout is retained for final success and
recovery. This scorer is distinct from the LLM-based pre-execution verifier. Appendix C.1 specifies
the procedure and benchmark-specific semantics.

2.2   Prefix-Level Reliability Metrics

For rollout i, let Ti denote the number of evaluated tool-action slots and let Yi ∈ {0, 1} indicate
benchmark-defined final task success. For ordinary trajectories, Ti is the number of predicted tool
invocations. If an agent terminates before emitting any tool call in a selected tool-use task, the
instrumentation represents this as a length-one terminal no-tool action; that action is executable only
if the benchmark permits task completion without tool use. Thus Ti ≥ 1 for all evaluated rollouts. We
use T and Y without subscripts for the corresponding random variables, and hats denote finite-sample
estimates over the evaluated rollouts.

2.4   First-Failure Annotation Protocol

When FEDi ≤ Ti , we annotate the action at the first invalid prefix with one primary cause: schema
failure, dependency failure, precondition failure, state-consistency failure, or information failure.
The labels are mutually exclusive by deterministic tie-breaking in that order, so category counts sum
to the RR-Eligible set. These labels are diagnostic only; they are not used to compute PEC, TER,
AUC-PEC, or RR. The taxonomy is benchmark-agnostic but reflects stressors emphasized by BFCL,
ToolSandbox, NESTFUL, FAIL-TaLMs, and function-calling robustness studies [3–5, 13, 17].

2.5   Validation Intervention

Dual-Loop is included as a controlled validation intervention, not as the main architectural claim.
Given the user goal, tool schema, and a compact state summary, a planner proposes a structured plan.
A verifier checks tool existence, schema conformity, explicit preconditions, and variable bindings. If
verification fails, the planner revises the plan using verifier feedback; once verification succeeds, the
approved plan conditions a ReAct executor, which alone issues environment tool calls. Planner and
verifier messages are therefore method-side computation, not benchmark tool actions, and all prefix
metrics are computed on the executed tool trajectory. The intervention follows planner-executor and
verifier-guided generation work, but here serves as a stress test for the evaluation protocol [18–22].
Appendix D gives the schematic.

2.6   Benchmarks and Experimental Setup

We use BFCL v3 and ToolSandbox to test multi-step function-calling correctness and stateful on-
policy interaction. BFCL v3 provides multi-turn function-calling scenarios under a standardized
interface, making it a test bed for schema, ordering, and cross-step dependency errors [3]. ToolSand-
box adds stateful tool execution, implicit state dependencies, an on-policy user simulator, and dynamic
intermediate/final milestone evaluation, making recovery after intermediate failure observable during
the rollout [4].
For each benchmark, we evaluate a stratified sample of N = 200 instances. The BFCL v3 subset
is stratified uniformly over the four multi-turn categories used in this study: multi_turn_base,
multi_turn_miss_func, multi_turn_miss_param, and multi_turn_long_context, with 50
tasks from each. The ToolSandbox subset contains 200 supported open-source scenario templates


                                                    5
selected by a deterministic greedy multi-label stratifier over scenario-category labels. Sampling
is performed once per dataset, and the same task IDs are reused for every model and method, so
all method comparisons are paired at the task level. The BFCL-v3/ToolSandbox grid comprises
200 × 2 × 3 × 4 = 4,800 evaluated rollouts across two datasets, three models, and four agent variants.
We report 95% task-level confidence intervals. Marginal-interval overlap does not establish paired
significance, and we do not infer paired effects from it. Compute resources for the hosted-inference
and local-orchestration components of the BFCL-v3/ToolSandbox grid are reported in Appendix E.
Both benchmarks are instrumented at the action level. For each rollout, we log whether each predicted
call is executable, the first failing step, its primary error label, and whether the episode later reaches
benchmark-defined task success. On BFCL v3, this requires prefix-by-prefix replay of the predicted
sequence rather than scoring only the terminal trace. On ToolSandbox, we derive the same quantities
from executed trajectories and benchmark-provided traces, so state transitions and downstream
recovery are observed directly rather than inferred post hoc.
We evaluate all 50 Airline and 114 Retail base-split tasks in τ 3 -bench under the text half-duplex
protocol (recorded version v1.0.1). This is complete coverage of those two base splits, not all
benchmark domains. One rollout per task, model, and method yields 1,968 Airline/Retail episodes.
Across the three benchmarks, the main grid contains 6,768 rollouts over 564 tasks per model–method
condition. Appendix F reports the full scalar metrics, uncertainty, costs, and a separate paired
verifier-sensitivity study. Task-level intervals describe variation across tasks under the fixed protocol,
not repeated-run variability within a task.

2.7   Agent Variants and Experimental Controls

We compare a nested intervention ladder with four variants:
1. ReAct: interleaved reasoning and acting without explicit plan validation [2].
2. Prompt Planning: a planner-first variant in which a plan is generated but not enforced during
   execution.
3. Plan-Conditioned ReAct: the generated plan is provided as an explicit control signal during
   execution.
4. Dual-Loop: the same plan-conditioned executor augmented with pre-execution verification.
Within each LLM condition, executor calls share the same model setting, tool specification format,
decoding strategy, and benchmark horizon cap. Planner and verifier calls occur before execution
and are counted as method cost rather than tool actions in Ti . Additional provider-specific decod-
ing and rollout settings are reported in Appendix E. We report three LLM conditions: GPT-5.4
(reasoning.effort=high), GPT-4.1, and Llama-4-Maverick-Instruct.

3.3   Transfer, Cost, and the Boundary of Validation

The τ 3 -bench audit again separates terminal outcome from prefix reliability (Table F.1). With GPT-
5.4, Plan-Conditioned ReAct has the highest final-success point estimate (0.51), while ReAct has the
highest TER/AUC-PEC estimates (0.95/0.95). With GPT-4.1, Prompt Planning leads final success
(0.51), while ReAct leads TER/AUC-PEC (0.84/0.91). With Llama-4, ReAct, Prompt Planning, and
Plan-Conditioned ReAct tie at the displayed final-success precision (0.18), despite TER spanning
0.52–0.60 and AUC-PEC 0.56–0.65. These are model-dependent point-estimate orderings, not claims
of paired significance.
The Airline/Retail audit does not establish the consistent validation advantage observed on BFCL-v3
and ToolSandbox. A possible explanation is that BFCL emphasizes pre-specified composition,
whereas interactive user feedback and state changes in τ 3 -bench can make advance plans stale. This
is a testable interpretation, not an identified causal mechanism.

changes mean tokens/cumulative agent-call latency relative to Plan-Conditioned ReAct by approxi-

exclude simulator and evaluator calls. Table F.2 gives all four methods and accounting details.

4   Conclusion

Reliable tool use is not only a question of whether an agent eventually succeeds, but whether its
trajectory remains executable as it unfolds. This paper introduced prefix executability as an evaluation
protocol for tool-using agents, formalizing PEC, FED, TER, AUC-PEC, and RR for variable-horizon
rollouts. Across the three-benchmark audit, prefix reliability and terminal outcome provide comple-
mentary information. Validation improves prefix reliability on BFCL-v3 and ToolSandbox, while
the Airline/Retail transfer audit and paired sensitivity study show that this benefit is environment-
dependent. Exact identities explain how high final success can coexist with frequent prefix failure,
and cost measurements expose the operational price of validation. Evaluations should therefore report
uninterrupted executability, recovery, terminal success, and agent-side cost together.
Although we report PEC, FED, TER, AUC-PEC, and RR as retrospective evaluation metrics over
completed rollouts, the underlying executable-prefix predicate is prefix-local. When available during
execution, it can be checked after each candidate tool action to support runtime monitoring, repair,
replanning, or human escalation before invalid state is propagated. Aggregated over rollouts, the
same signals can guide offline choices such as prompt design, validation budgets, and agent selection.
These uses remain complementary to the paper’s evaluation focus: prefix executability exposes
whether and where a trajectory becomes invalid, but it does not by itself certify semantic correctness,
safety, privacy, or fairness. Developing closed-loop agents and deployment policies that optimize
against these signals is an important direction for future work.


Limitations

The study is an audit rather than a complete leaderboard evaluation: BFCL-v3 and ToolSandbox
each contribute 200 sampled tasks, ToolSandbox is restricted to supported local-tool scenarios, and
τ 3 coverage is complete only for the Airline/Retail base splits. Task-level intervals do not measure
within-task repeated-seed variation. The main-grid tables provide marginal intervals; paired intervals
are reported for the separate verifier-sensitivity study. Fixed-cohort PEC reflects both reaching a
depth and retaining validity, so its decline is not an error-only statistic.
Executability assumes explicit schemas, preconditions, and benchmark-accessible state. Partially
observed web or GUI environments may require state estimation or learned preconditions, and exe-
cutability does not certify semantic correctness. We did not evaluate a matched schema-constrained-
decoding baseline, so the reported rankings are not established under such constraints. These
constraints can prevent malformed arguments, while prefix checking additionally covers object
existence, provenance, state preconditions, and transition acceptance.
The intervention combines validation/revision with extra inference. The sensitivity study varies
verifier capacity and budget, but its acceptance wrapper changes executor guidance; it does not fully
separate validation logic from compute or context effects. Per-method cost telemetry is available for
the τ 3 audit, whereas the BFCL-v3/ToolSandbox grid has aggregate runtime only. Broader claims
require additional domains, repeated runs, and matched constrained-decoding and repair controls.

Broader impacts. Prefix-level executability can improve oversight of tool-using agents by identi-
fying invalid API calls, unresolved dependencies, and state-precondition violations before they are
obscured by final-success scores. This is most useful in workflows where tool calls modify persistent
state, consume resources, trigger external actions, or require human escalation. The same diagnostics
may also make autonomous tool use easier to deploy in settings with privacy, security, fairness, or
service-access risks. Moreover, an executable trajectory can still be unsafe, biased, privacy-violating,
or misaligned with user intent. Prefix executability should therefore be treated as one reliability signal


                                                    9
and combined with domain-specific safety policies, privacy controls, security review, and human
oversight in consequential applications.

C     Deterministic Executability Checking and Recovery
C.1   Executability Checks and First-Failure Classification

The executability scorer is deterministic and separate from the LLM-based pre-execution verifier
used by Dual-Loop. The scorer evaluates the actual emitted actions against benchmark tool and
state semantics; no learned judge, human step label, or single gold action sequence is required.
The Dual-Loop verifier instead examines a proposed plan before execution and may change the
executor’s subsequent behavior. Its acceptance decision does not establish that the emitted trajectory
is executable.
For action aj , let Vj = 1 exactly when the tool is exposed, its arguments satisfy the declared interface
and validators, referenced values are available and type-compatible, required information has been
obtained, applicable state preconditions hold, and the benchmark accepts the transition. Otherwise
Vj = 0. The checker determines first failure as follows.
1. Initialize replay from the benchmark’s initial state. Available values comprise the prompt and
   benchmark-visible initial values. Initialize FED = T + 1.
2. Process emitted actions in order. Resolve the selected tool; an unavailable tool is a schema/tool-
   availability failure. For an exposed tool, check argument binding, declared types, and registered
   validators.
3. Check referenced values for absence, stale bindings, or incompatible types; these are dependency
   failures. Check whether required task information has been obtained, and whether applicable state
   preconditions hold.
4. If these checks pass, execute the action against the replay or sandbox state. A rejected transition is
   a state-consistency failure. For an accepted transition, record the output, update available values,
   and advance the state.


                                                   14
5. At the first failed predicate or rejected transition, set Vj = 0 and FED = j. Choose the first
   applicable diagnostic category in the precedence order below, then stop prefix replay. Retain the
   full observed rollout for benchmark-defined final success Y and RR.
6. If every action satisfies the predicate, retain FED = T + 1. A terminal no-tool action is executable
   only when benchmark semantics permit completion without a tool call.

The diagnostic precedence is
       schema −→ dependency −→ precondition −→ state-consistency −→ information.
The tie-break assigns one primary cause at the first failed action; it changes neither action validity nor
FED, PEC, TER, AUC-PEC, RR, or final success. In particular, the diagnostic ordering is distinct
from the order in which applicable conditions are checked.
BFCL-v3 evaluates prefixes by replay in a copied state under the case-specific function namespace
and benchmark evaluator semantics [3]. ToolSandbox uses tools visible at the relevant turn, their
registered validators, and the recorded execution outcome and state transition [4]. These benchmark-
specific semantics ground the same executability predicate. The metrics then aggregate the resulting
(Ti , FEDi , Yi ) records deterministically.
Stopping the first-failure replay does not truncate the observed episode or replace its final outcome.

D     Dual-Loop Validation Details
This appendix specifies the validation intervention in Section 2.5. Only the evaluated executor
trajectory, including the terminal no-tool action defined in Section 2.2, enters the prefix metrics.
Planner and verifier messages influence subsequent behavior and cost but do not contribute to Ti .
Figure D.1 summarizes the information flow.

D.1   Objects and Information Boundary

Let x denote the user goal, U the available tool specification, and s0 a compact summary of benchmark-
visible state before execution. Dual-Loop uses a planner P , verifier V , and executor R. At validation
iteration j, the planner proposes a finite candidate plan
                                                   (j)          (j)
                                        z (j) = (z1 , . . . , zMj ),
where each step describes an intended tool-level operation, argument values or constraints, and
dependencies on prior planned steps, observations to be produced by those steps, or user-provided
information. The plan length Mj need not equal the eventual executed horizon Ti : the plan is
conditioning context, not the object being scored.
The verifier maps (x, U, s0 , z (j) ) to either acceptance or a structured rejection record. The planner
and verifier do not receive the benchmark reference trajectory, hidden final-success label, or future
observations. After validation terminates, the executor interacts with the benchmark and emits
                                        τ̂i = (ai,1 , . . . , ai,Ti ).
The evaluator scores this emitted trajectory directly. Thus, if the executor deviates from a verified
plan, terminates early, or emits an invalid call, the metrics reflect the emitted actions exactly as they
occurred.

D.2   Verifier Checklist

The verifier is designed to reject candidate plans that contain predictable sources of non-executable
prefixes before any environment action is taken. It applies the following local checklist, aligned with
the first-failure taxonomy in Section 2.4:
1. Tool and schema validity. Each planned operation must refer to an available tool in U, in-
   clude required arguments, avoid unsupported arguments, and satisfy declared type or formatting
   constraints.
2. Dependency resolution. Values referenced by a planned step must be available from the prompt,
   the initial state summary, or an earlier planned step. The verifier rejects forward references, stale
   bindings, and type-incompatible reuse.


                                                     16
3. Information availability. Required user information or lookup results must either be present,
   requested before use, or represented as a dependency on an earlier planned step. This check
   catches plans that use information before collecting it.
4. Explicit preconditions. If a tool requires prior authorization, a preceding state update, or a
   specific object to exist before use, the plan must satisfy that prerequisite before the tool is called.
5. State consistency. Planned state mutations must be compatible with benchmark-visible state and
   with state changes induced by earlier planned steps. Examples include rejecting updates to absent
   objects or operations that consume unavailable resources.
The checklist is intentionally local. It is not a proof of global optimality, and it does not replace
benchmark replay after execution. The benchmark-side evaluator remains the authority for FED,
TER, final success, and RR.


D.3   Repair Loop and Iteration Budgets

If the verifier rejects a candidate plan, its feedback identifies the earliest detected failing step, the
failed check, and the information needed for repair when that information is available from x, U, or
s0 . The planner then proposes a revised candidate before any environment-facing action is emitted.
In the BFCL-v3/ToolSandbox experiments, the validation loop is capped at Kval = 5 candidate plans.
If no candidate is accepted within this cap, the validation stage returns a failure flag and the executor
receives no accepted plan as a strong constraint. The rollout is not discarded; any environment actions
subsequently emitted by the executor are scored in the same way as all other rollouts. Cap exhaustion
is therefore method-side behavior, not a prefix failure.
The validation cap is separate from the ReAct execution cap. For BFCL-v3 and ToolSandbox, we use
Kexec = 10 ReAct action iterations for the environment-facing executor. This separation is important
because the two loops bound different resources: Kval limits unscored pre-execution search over
candidate plans, whereas Kexec limits the scored action horizon available for multi-step tool use. A
validation iteration does not increment Ti ; only executor-emitted environment actions, or the terminal
no-tool action described in Section 2.2, contribute to Ti and to PEC, FED, TER, AUC-PEC, and RR.


D.4   Metric Accounting and Controls

The following conventions keep the intervention aligned with the prefix-level definitions:
1. Candidate plans, verifier decisions, and verifier feedback are not benchmark actions. They affect
   metrics only through the executor’s subsequent environment-facing behavior.
2. FED is computed after execution from τ̂i . A verified plan that later leads the executor to an invalid
   call is counted as an ordinary prefix failure.
3. RR is computed only for rollouts with FEDi ≤ Ti . Rejected candidate plans before execution are
   not RR-eligible because no benchmark prefix has failed.
4. Validation does not modify benchmark state before execution. It can improve PEC, TER, or
   AUC-PEC only by changing the environment-facing actions emitted by the executor.
Within each benchmark–model condition, all variants use the same task identifiers, tool specifications,
executor horizon cap, and decoding rule. The Dual-Loop–Plan-Conditioned ReAct comparison
measures the joint effect of validation, revision, and their additional inference cost under matched
executor conditions. The scored trajectory semantics are the same across variants. Appendix F gives
the verifier-sensitivity results and experimental controls. Planner and verifier calls are outside the
scored trajectory, but should be included when comparing token use, latency, or deployment cost.


D.5   Limitations of the Intervention

The verifier can miss hidden-state constraints, underspecified intent, or semantic requirements
outside the tool interface, and can reject executable alternatives. Pre-execution validation also adds
inference cost. The prefix metrics characterize how Dual-Loop’s effects vary across environments
and configurations (Appendix F).

E     Additional Experimental Settings and Compute Resources
Decoding and rollout settings. The following decoding settings and aggregate runtime apply to
the 4,800-rollout BFCL-v3/ToolSandbox grid. All LLM conditions used the least-stochastic provider-
supported configuration. For GPT-4.1 and Llama-4-Maverick-Instruct, we set temperature to 0, used
top-p = 1 when exposed, and disabled presence and frequency penalties. For the GPT-5.4 reasoning
condition, unsupported sampling controls were not set; instead we fixed reasoning.effort=high
and kept the remaining provider-exposed generation controls at their defaults. To equalize generation
budget, every planner, verifier, and executor call used a 4,000-token response cap; for APIs that
distinguish hidden reasoning tokens from visible text, this cap is applied to the provider’s total
output-token budget. The environment-facing ReAct execution loop was capped at Kexec = 10 tool-
action iterations for every ReAct-style agent variant, while Dual-Loop additionally used the separate
pre-execution planner–verifier budget Kval = 5 described in Appendix D; validation attempts are
method-side computation and are not counted as tool actions in Ti .

Compute resources. Our experiments evaluate agent rollouts rather than train or fine-tune models.
All LLM inference was performed through hosted model APIs; the local machine only orchestrated
benchmark execution, tool-state updates, trajectory logging, and metric computation. Model inference
was served by provider-managed accelerator infrastructure behind API endpoints, so per-request
GPU type, GPU count, and accelerator occupancy were not exposed to us. We therefore report local
orchestration compute separately from hosted inference compute. The BFCL-v3/ToolSandbox grid
contains 200 × 2 × 3 × 4 = 4,800 rollouts across two datasets, three models, and four agent variants.
A CPU-only local worker is sufficient for the evaluation harness; the BFCL-v3/ToolSandbox runs
used a Linux worker with 16 vCPUs and 64 GB RAM, with no local GPU allocated. Wall-clock time
was dominated by remote model latency and API rate limits rather than local computation; using
16 asynchronous API-request workers, the 4,800-rollout BFCL-v3/ToolSandbox grid completed in
approximately 72 hours. Offline computation of PEC, FED, TER, AUC-PEC, RR, and bootstrap
confidence intervals for this grid completed in under 1 hour on the same machine.
The four-method, three-benchmark audit comprises 4,800 BFCL-v3/ToolSandbox rollouts and 1,968
Airline/Retail rollouts, totaling 6,768. The verifier-sensitivity study uses separate paired runs outside
this total. The approximately 72-hour runtime applies only to BFCL-v3/ToolSandbox. Appendix F
reports agent-side token and latency measurements for Airline/Retail and cost differences for the
sensitivity study, excluding simulator and evaluator calls.
